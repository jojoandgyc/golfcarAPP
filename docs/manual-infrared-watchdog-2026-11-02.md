# 手动控制超时与红外回执兼容修复

日期：2026-11-02（Asia/Taipei）。App：`1.8.2-drive-infrared` / versionCode `13`。

## 现场结论与证据

截图首次异常发生在本地时间 14:43:50（日志 UTC `06:43:50.734870Z`）：`drive.transaction_failed / SessionError: Control watchdog expired`。

手机日志表明该次使用本地地址 `172.16.16.82:22`，初始零速 ACK 成功；seq8 的 RTT 达 406 ms，seq10 是已确认的停车请求，seq13 返回板端 watchdog 错误。seq13 发出后约 71 ms 收到错误，`lastAckSeq=12`，最后 ACK 距离错误只有约 73 ms。这说明“刚收到上次回执”不足以证明板端仍有完整的 600 ms 租期。旧日志每秒汇总一次，无法精确重建每个包的板端到达时刻，不能据此认定每次超时都由红外或某一段网络单独造成。

旧调度在每次 ACK 后另等 100 ms。板端截止从上次合法请求到达时计算，下一次请求间隔包含串口处理、ACK 回程、额外等待和下一次去程，网络抖动时可能超过 600 ms。

板端存在一份未同步到本仓库的红外改动。其正常红外保护会将实际速度返回 `0/0`，而旧 App 要求 ACK 速度严格等于非零请求，这会产生另一个确定的协议故障。修复从现场完整代码合并，保留三路方向映射、急停方式、闩锁、回中解除及允许撤退规则。

只读测量三路 IIO 输入 10 轮，每轮约 0.08–0.20 ms，输入均为 `1`。当前没有观察到红外读取阻塞；未主动触发传感器或实车电机。

## 修改

- 心跳周期从发送开始计算。慢 ACK 消耗本周期，已经超过 100 ms 时立即采样最新目标和停止请求；仍然只有一个在途请求，不积压旧运动指令。
- 新板端 READY 宣告 `infraredSupported`，ACK 显式包含 `infraredBlocked` 与 `infraredDirections`。仅已协商红外保护、非零 drive 请求、实际完整零速、stopped=true、合法非空方向，才允许覆盖目标。旧板和其他 ACK 保留严格速度匹配；字段缺失、伪造、部分零速和错误类型仍退出。
- 正常红外保护显示“红外保护已停车”，保留会话。原有闩锁及回中规则继续由板端执行。
- 红外轮询后重新检查期限，不能用轮询前剩余时间继续等或接受已经过期的缓冲请求。
- 板端新增 `app_drive_diagnostic_logs/` 后台结构化日志，记录请求间隔、处理耗时、IR poll 耗时、最后合法 seq、首错、清理与退出。READY 的随机 `runId` 与 App 诊断关联；不记录滚动 token 或原始请求帧。
- App 发送/ACK 汇总/失败增加 `sendGapMs`、`lastAckRttMs`。日志失败不影响停车；沿用 7 天/20 MB、有界队列及脱敏写入机制。

600 ms 板端 watchdog、900 ms App 普通 ACK 超时、串口时限、失焦停用和人工重新启用规则保持原样。传输延迟真的超过保护期限时仍应停车退出，不能通过放宽期限掩盖。
